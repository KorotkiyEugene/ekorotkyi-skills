# Writing research reports

The report of an R&D work is an argument that runs from a question to measurements and
back: the introduction promises, the methods make the promise checkable, the results pay
it, the conclusions count what was paid. Every chapter has one job, and a reader who
examines the work (a committee member, a reviewer, the engineer who inherits it) must be
able to check each claim without the author in the room. This skill gives the genre its
shape. `writing-technical-docs` governs the prose (derive, define, illustrate, no dashes),
`reporting-experiments` governs the results, `designing-research-studies` is where the
hypotheses and the protocol the report describes were fixed. The structure follows the
public thesis-writing guides for technical fields (the Tampere University guide for
technical fields is the one this skill distils, with the IMRaD convention underneath);
the rules below are the ones drafts broke most often.

## Write from artefacts, in this order

The text is assembled from things that already exist, never from memory:

1. **The review chapter** from the literature protocol and its verified bibliography
   ([references/literature-review-protocol.md](references/literature-review-protocol.md)).
2. **The methods chapter** from the code, the configurations and the design document:
   every parameter in the text is a value in a configuration file, every protocol
   sentence is a line of the evaluation code.
3. **The results chapter** from tables generated by scripts out of run logs
   (`reporting-experiments`), by condition band, with the discarded candidates.
4. **Conclusions, then the abstract, then the introduction**, last and in that order,
   so that what is promised is exactly what was delivered.

Keep the sources as plain text under version control, one file per chapter, and build
the submission format with a script that numbers chapters, sections, figures, tables and
equations, resolves cross-references by key, and builds the bibliography from a verified
database through a key map. A number typed into prose, or a section number typed by
hand, drifts the first time anything moves; a built number cannot.

## The introduction: one paragraph per question

The introduction answers a fixed set of questions, each in its own labelled paragraph,
because the examiner looks for each by name. It is two to four pages, contains no
results and no method detail, and every number in it carries a citation.

| Paragraph | What it answers |
|---|---|
| Relevance | What problem, for whom, what the best known approach achieves (a number with its condition and citation), what the application needs, why the gap can be closed now. |
| Aim | One sentence: to improve *what* by *what means*. Adjectives such as "efficient" or "fast" commit the work to measuring them. |
| Tasks | Three to five, each maps to a chapter and to a hypothesis, each phrased as a verb with a checkable outcome. |
| Object and subject | The process studied, and the methods within it that the work changes. |
| Methods | The named disciplines and techniques, including the experimental ones (controlled comparisons, several seeds, evaluation by condition band). |
| Scientific novelty | Each item: "proposed / improved / developed ... unlike known works where ...": the difference to prior work is in the sentence, not implied. |
| Practical value | The artefacts: software, hardware project, dataset, reproducible protocol. |
| Structure | One sentence per chapter, and the first figure of the work: the system with its inputs, outputs and the author's contribution highlighted. |

## The review chapter: organised by question, closed by a gap table

A review that lists papers one after another is a reading log. A review chapter is
organised by the questions the study asks (each task, each candidate axis, the
platform), and each section opens by stating the task and the criteria by which a
solution is judged, so that the papers that follow are read against them.

- Every number quoted from a paper carries its conditions: dataset, input size,
  condition band, hardware, protocol. Numbers from different conditions are placed in
  one table only with a column that says whether they are comparable.
- Similar works close with a comparison table (work, data, method, result, condition,
  what it does not cover).
- The chapter closes with two generated-by-hand tables that the rest of the work argues
  from: the **gap table** (what the literature has | what is missing | what this work
  does) and the **hypotheses table** (hypothesis | the result that refutes it), copied
  from the design document, not rewritten.
- The point of reference (the closest reproducible work) gets its numbers reproduced
  with arithmetic in the text (from its latency per fragment to the sample rate it
  sustains), because the reader will check that derivation first.
- Chapter conclusions restate what the review established and what it leaves open.

## The methods chapter: enough to repeat it without the author

- Alternatives and the reason for the choice, for every design decision the design
  document made; the discarded alternatives are named with their reason.
- Data described so that its provenance is beyond doubt: source, licence, size, the
  split rule (by record or session, never by sample), what is identical across runs.
  A generated dataset gets the physical derivation of its parameter ranges and the
  statement of what it does not model.
- The evaluation protocol in full: metrics with formulas and the script that computes
  them, condition bands with their edges, seeds, how operating points are chosen (on
  validation, frozen before the test), how baselines are calibrated, what one run stores.
- Versions of tools, configurations, seeds and the command that reproduces each table,
  in the text or in an appendix the text points to.
- Novelty is made explicit relative to prior work in the place where the method is
  described, not only in the introduction.

## The results chapter and the conclusions

Results follow `reporting-experiments`: conditions derived, the measurement ceiling
named, metrics calibrated, one bold finding per paragraph with its mechanism and
control (or "not explained" with candidates), a section on what the tests do not show,
numbered conclusions each with its number. Three additions for the genre:

- **By condition band, always.** The table has a column per band; the sentence that
  averages over bands is replaced by the band where the method fails and the band where
  it is safe.
- **The sieve is reported.** Every candidate that was discarded appears with the
  checkpoint that discarded it, its number and the criterion; a candidate that vanished
  between the design and the results is the first thing a reviewer asks about.
- **Qualitative error analysis.** A few examples of what the method gets wrong, with the
  figure that shows them, because the number alone does not tell the reader which failure
  mode the next work should attack.

Conclusions are the chapter the examiner reads second, after the abstract: the main
results with their key numbers and conditions, what they mean, the limitations, the
recommendations for use, the further work, and a summary table of the work (aim,
methods, results, strengths, weaknesses, time spent, cost). The abstract is one page,
written last: aim, materials, methods, numeric results, conclusions, no citations, no
figures, nothing that is not in the body.

## Register and terminology of the genre

- Impersonal scientific register: "the work proposes", "it was measured", "it is shown";
  no first person, no diary ("we then tried"). Decisions are stated with their reasons,
  not narrated as events.
- Headings name the subject of the analysis as noun phrases ("Analysis of detection
  methods", "Evaluation protocol"), never a person, a metaphor, a status or working
  jargon ("Our approach", "What we do next", "Baseline").
- One canonical term per concept. Keep a glossary file in the repository with three
  columns (the term, the foreign term it translates, the forms that are banned) and
  sweep the sources for the banned forms before delivery. A reader who meets two words
  for one thing assumes two things.
- Every claim of "better", "faster", "lighter" carries a number, a unit and the
  condition; every borrowed figure, table or idea carries a citation beside it.
- Percentage differences are percentage points. Numbers put on a scale: instead of
  "cheap", the price; instead of "small", the parameter count.
- For a Ukrainian text, `writing-technical-docs/references/ukrainian-engineering-prose.md`
  (its research vocabulary section included) is read before drafting; the document is
  written in Ukrainian from the start, not translated.

## Figures, tables, formulas, code, citations

The institutional rules that drafts broke most often are collected in
[references/report-structure-and-checklist.md](references/report-structure-and-checklist.md):
every figure and table cited and discussed with its numbers; figures computed by kept
scripts from the actual models and data, not drawn by hand; axis labels with units and
in the document's language; tables with the best value marked and the magnitude in the
header; formulas numbered when referenced with every symbol defined once; code up to ten
lines as a formula, up to a page as a figure, longer in an appendix; one numeric
citation style, primary sources, preprints marked, every bibliography entry verified by
a script (identifier resolves, metadata matches), and no entry without a citation in
the text.

## Before submission

Run the checklist in the reference file. The items that catch the most:

- The hypotheses and tasks in the introduction are the ones the results test and the
  conclusions count. (Diff the three lists.)
- Every quantitative claim has a number, a unit, a condition and a source.
- Operating points were chosen on validation; the test split was used once.
- Results are by band and by split, not only averaged; failures and quantisation losses
  are reported like successes.
- For each key result the alternative explanations were considered in the text.
- The methods description, with the commands and configurations, suffices to repeat the
  work; full tables are in appendices the text points to.
- Terminology is consistent and swept; abbreviations are expanded at first use; the
  prose has no dashes as connectives and no status labels in headings.

## Common mistakes

| What happens | What to do instead |
|---|---|
| The introduction promises three contributions; the results chapter tests two | Write the introduction last, from the results; the third contribution is removed or becomes a task for further work. |
| The review is a chronological list of papers | Organise by the study's questions; close with the gap table and the hypotheses table. |
| A number in the prose differs from the table | Numbers come from the generated table; after a re-run, grep the sources for every changed value. |
| "The model achieves 92 % accuracy" | "92 % averaged over −20...20 dB, 31 % in the −15...−10 dB band": the band is the result. |
| A candidate from the design is missing from the results | It is reported with the checkpoint that discarded it and the criterion; the sieve is a result. |
| Headings like "What we did", "Our baseline", "Point of reference" | Noun phrases naming the subject: "Reference detector and its reproduction". |
| "Faster and more efficient" | The factor, the unit, the condition, and the measurement that produced them. |
| A bibliography entry nobody can resolve | Every entry verified by script against its identifier; unverifiable entries are removed or replaced by a primary source. |
| The abstract mentions a result the body does not contain | The abstract is written last and contains only what the conclusions count. |
